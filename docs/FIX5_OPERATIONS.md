# Fix5 operating contract and verification notes

## Observation compatibility
The single policy contract is `sentinel.policy.v2`, **62** dimensions, defined by `policy_schema.OBSERVATION_DIM`. Training, shared live observation construction, simulator inference and the bundle checker use this contract. The execution adapter receives normalized actions, not an alternate observation vector. `sfx check` and `load_bundle` reject old metadata and actual ONNX policy input widths other than 62 before inference. Forging metadata around a 47-dimensional network does not bypass this gate. The model registry marks unknown/old metadata **retired, incompatible**. Archived releases are not deleted. Model health is not evidence of profit.

## Four independent owner overrides
Risk saves separately for demo and real. Fixed take profit, fixed stop loss, daily profit target and daily loss limit each have their own enable switch. OFF or empty is unset; no number is required to save. Units are account money or percent of the session pool. The required precedence is **owner override wins**, for newly opened positions and for enabled fixed levels on existing owned positions. OFF must preserve the model's levels. An unset fixed stop never removes the model's mandatory server-side protective stop. Stops may still be subject to broker tick, minimum-distance and freeze constraints; rejected changes must be reported, never treated as success.

Daily PnL is realized net deals (including costs) plus current floating PnL during a **UTC day, 00:00–24:00 UTC**. Reaching either enabled daily threshold blocks new entries. Optional 'also close all open positions' defaults OFF; protective stops remain in force. At next UTC day the halt resets automatically; the owner can clear it manually. Test-only day shifts must never affect real accounts.

The preceding paragraphs specify the required behavior; inherited local tests alone do not prove the live broker paths. V2 remains subject to fresh demo verification, including monetary conversion and open-position precedence. Do not infer broker acceptance from this document.

## Training and release
Each authorized pair cycle must train the full **5,000,000** steps; there is no plateau/early-stop release rule. Persisted checkpoints resume existing weights and observation shape, never reset to zero. Every 50,000 steps a purged validation window, separate from training and locked final hold-out, selects the best checkpoint by risk-adjusted growth with drawdown and activity reported. Profit is judged only out of sample. After the target, only that best-validation candidate may be evaluated on the final hold-out, including simple and do-nothing baselines, normal and 1.5x costs, drawdown and trading-days activity gates. Count hold-out looks. If gates fail, show **no proven edge, not released**, not a tradable release. No unbounded seed retries are authorized; default retry budget is zero unless explicitly configured.

The resumed session found the original EURUSD v1 chain already stopped at a durable **900,000-step** checkpoint because evaluation raised `invalid volatility`. It has not been reset or overwritten. The original H3/V4 claims are not fresh integration proof; the training repair/resumption and actual best-checkpoint acceptance still require verification.

## Measured ETA
Use the last N=5 verified checkpoints **of the same active pair/version**: `steps_per_minute = (last_step - first_step) / ((last_time - first_time)/60)`. `remaining_minutes = max(0, target-done) / steps_per_minute`. Checkpoint-to-checkpoint wall time includes measured handover gaps; do not add a gap twice. If computing active-job throughput separately, include the measured restart gap. With fewer than two verified checkpoints display **measuring...**. Show rate, elapsed, remaining and estimated finish in the browser/owner timezone. Queue totals require a known rate for every waiting pair; never copy EURUSD's rate to unknown pairs. The original 400+ hour error was a hard-coded 4.75 **hours per 50,000 steps**, confusing job wall duration with checkpoint duration. The current inherited queue ETA requires audit against this rule.

## MT5 credential flow
Settings seals each changed value with the GitHub repository public key using libsodium sealed boxes and writes **GitHub Actions repository secrets**, which bot.yml actually consumes. Secret names: `MT5_PASSWORD`, `MT5_DEMO_LOGIN`, `MT5_DEMO_SERVER`, `MT5_REAL_LOGIN`, `MT5_REAL_SERVER`. An empty password leaves the stored value unchanged. Never send plaintext passwords to Worker/D1, logs or the repository. Worker stores only non-password account configuration. The current runner retains launch-time credentials; new values take effect on the next READY handover/restart. Login tests are read-only; real-account tests must never place orders. A transport/reporting failure is not a successful login.

## Market sessions / weekends
The intended/default rule is no new forex orders when the **broker's trading session is closed**, not an assumption that all weekdays are open. Synthetics with open 24/7 sessions are unaffected. Turning the weekend preference on cannot make a closed broker session executable. The simulator must omit closed-session entries and preserve gap/rollover costs on held positions. Training computation itself may continue on historical data at any time once owner-started; it must not fabricate weekend candles or initiate a new cycle on a cron. Fresh data must be loaded before each authorized new cycle. Broker-session integration and simulator behavior remain subject to V6.
